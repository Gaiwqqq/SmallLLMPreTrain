# 评测与推理：用真实请求判断“能不能交流”

loss 下降说明模型更擅长预测某一文本分布，不保证它正确完成用户请求。这里要把训练目标与最终使用目标重新接起来。

## 为什么先固定题目，再看模型答案？

看到答案以后再挑“模型做得好的题”，会夸大能力。所以在正式训练前冻结 40 项开发题与 120 项最终题，保存内容哈希。开发题用于选配置，最终题用于验收。

最终题六类，每类 20 项：日常对话、常识、指令遵循、改写、摘要、三轮上下文。它们对应实际用途，而不是只测一种容易的续写。三轮题把模型的真实回复接回下一轮，不放入事先写好的正确 assistant 答案。

## 自动检查与语义评分分别回答什么？

| 检查 | 能识别的例子 | 不能因此证明什么 |
|---|---|---|
| 空回答 | 输出没有内容 | 非空就一定有帮助 |
| 复读 | 大量重复四词片段 | 不复读就一定正确 |
| 角色泄漏 | 输出新的 user/system 角色标签 | 没有标签就一定遵循指令 |
| 上下文限制 | 剩余长度不够完成生成 | 长度够就一定记住前文 |
| 语义审阅 | 事实、格式、原意与上下文是否符合 rubric | 少量用例代表全部真实使用场景 |

例如，要求摘要保留“会议延期到周五”，回答很流畅却写成周四，也应失败。要求输出三条建议，答案内容不错但给了七条，同样可能不满足该题标准。

每项语义评分有唯一 ID、布尔 pass 和引用实际答案的理由，不能靠模型看起来“像在聊天”给分。未审阅的 `semantic_pass=None` 是未评分，不是通过。

## 为什么设总分和分项两个门槛？

首轮目标：总通过率至少 70%、每类至少 60%、结构正常至少 90%。总分防止整体表现差，分项门槛防止靠简单闲聊掩盖摘要或上下文能力差。它们是本项目的入门交付目标，不是行业统一合格标准，也不是已完成结果。

测试未达标就公开失败例子和实际指标。若继续修改模型，原测试集已经被看过，之后的结果不应仍被宣传为完全未见的独立验收。

## 辅助基准为什么还要单独做？

Base 与 Chat 使用相同设置评估 HellaSwag、PIQA、ARC-Easy，各限制 200 项，作为预算内的辅助信号。这些题偏向选择/续写类能力，不直接测多轮聊天。限制样本量也意味着结论范围有限。

Base/Chat 对照可以观察 SFT 是否带来某些能力变化，但只凭一轮结果不能把所有差异都解释成 SFT 的一般规律。环境在 `envs/evaluation`，避免评测依赖改变训练环境。

## 为什么小模型推理只用一张卡？

训练用四卡分担数据；单次回复通常没有那么多独立样本，而且模型能放进一张卡。把一次请求拆到多卡可能增加通信开销。因此 vLLM 首版 `tensor parallel=1`，部署在独立 `envs/inference`。性能是否达标仍需要实际 smoke 和延迟测量。

CLI 支持 `/reset`、`/quit`；上下文不够时提示清空历史，避免静默删掉用户认为模型还记得的内容。服务绑定回环 8000 端口，通过 SSH 访问。

## 操作与成果

```bash
# Chat 模型就绪后执行；输出是待审阅答案，不是自动验收报告。
dummym-evaluate --model "$PRETRAIN_ROOT/exports/chat" \
  --suite evaluation/chat_test.jsonl --output "$PRETRAIN_ROOT/runs/evaluation/test.jsonl"
dummym-chat --model "$PRETRAIN_ROOT/exports/chat"
bash scripts/inference/serve.sh "$PRETRAIN_ROOT/exports/chat"
```

语义评分格式和汇总命令见 [题集说明](../evaluation/README.md)。题集数量、唯一性与哈希检查通过；正式 v2 的生成与逐题语义审阅均已完成：15/120（12.5%），accepted=false，见 [最终报告](final_delivery.md)。上面的命令是复现示例，不需覆盖已经保存的评测回复。

交付时应有 Base/Chat、Tokenizer、完整恢复点、模型卡、统一评测与失败例子。让模型可加载是工程成果，让它能正确交流则需要这份独立能力证据。

推理依赖故障的设计、恢复命令与已验证结果见 [推理恢复记录](inference_recovery.md)。服务可用不替代聊天语义评分。

## 哪份模型、哪套题？

首轮 Chat 使用 `exports/chat` 与旧 120 题；正式 v2 使用 `exports/curriculum-v2-formal` 与训练前冻结的 `evaluation/chat_test_v2.jsonl`。正式 v2 的原始回答和逐题判定在 `evaluation/reviews/formal_v2/`，40 项 dev 单独评分，不能并入 120 项最终分数。不同 test 的分数不能直接作训练趋势比较。

验收使用正式 v2 的离线生成记录；当时回环服务仍加载旧 `exports/chat`，没有为了读取现有答案而换模型或重复生成。模型、完整训练恢复点与评测证据的对应关系见 [交付清单](artifacts.md)。
