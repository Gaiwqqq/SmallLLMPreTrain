# 首轮交付：完成了训练，但聊天能力未达标

## 已经取得什么成果？

213M 参数模型从随机权重开始训练，使用自行训练的 32k Tokenizer。预训练实际读取约 77 亿 token，完成 14,687 次参数更新，耗时约 10.05 小时，最终验证 loss 为 2.640921。正式 SFT 使用 451,821 个训练会话、4,564 个验证会话，训练两轮，共 7,060 步，耗时约 3.66 小时，最终验证 loss 为 1.149027。

这些 loss 使用不同数据和监督方式，不能直接比较为“能力提升了多少”。预训练学习文章的下一 token；SFT 只监督 assistant 回复。loss 下降表示更能预测对应验证数据，不保证事实正确、遵循输出格式或记住前面的对话。

Base 与 Chat 导出此前已经上传至 [私有 ModelScope 仓库](https://modelscope.cn/models/GaiWeiqi/SmallLLMPreTrain-English)。正式训练的恢复点包含优化器、学习率调度器及各 rank 随机数状态；恢复训练应使用完整 Trainer 快照，聊天推理使用 `exports/chat`。

## 实际验收结论

120 题、六类各 20 题，46 题通过，总通过率 **38.3%，accepted=false**。目标为总通过率至少 70%、每类至少 60%、结构正常率至少 90%。

| 类别 | 通过数 | 通过率 | 观察与解释 |
|---|---:|---:|---|
| 日常交流 | 10/20 | 50% | 有些问候清楚，但实用建议、相关性和约束不稳定 |
| 事实知识 | 3/20 | 15% | 出现正确关键词时，后续仍可能编造相关事实 |
| 指令遵循 | 5/20 | 25% | “只输出”、计数、大小写、JSON 等格式约束经常失败 |
| 改写 | 18/20 | 90% | 17/20 原样复制输入，分数不能证明会真正改写 |
| 摘要 | 10/20 | 50% | 部分复制多句原文或写错时间，未完成单句压缩 |
| 多轮上下文 | 0/20 | 0% | 无法稳定保留用户姓名、物品及更新后的数量 |

自动结构检查仅发现 1 题复读，结构正常率达到 99.2%。它只能筛查空回复、明显复读和角色泄漏；无法知道事实是否正确。把其余 119 题视为通过，会掩盖核心问题。

所有回复已逐题读取，理由保存在 `runs/evaluation/test-reviews.jsonl`，原始回复为 `test.jsonl`，聚合结果为 `report.json`，评分政策与局限为 `review-method.json`。这是 Codex 辅助的 rubric 审阅，尚不是独立人工认证，日常交流及错误严重性的判断仍含主观性。

## 工程故障与模型不足分别怎么处理？

正式 SFT 的 NCCL 超时发生在全量 CPU 预处理阶段，处理时间超过其他 rank 的等待窗口；修复为先准备 Arrow 数据、校验哈希，再启动多卡训练。后来 vLLM 的 Tokenizer 接口错误由依赖兼容问题引起，固定依赖后，预检、GPU 离线推理和 HTTP 请求均通过，详见 [推理恢复](inference_recovery.md)。这两种故障不需要通过增加训练轮数来解决。

2026-10-06 本次续接已通过 SSH 核实：8000 端口服务加载 `exports/chat`，四卡没有训练负载。服务能返回回复，但模型尚不能可靠交流。

## 下一步已经明确

用户已授权下一轮格式/状态课程 SFT。采用两个受控短跑，保留当前 Chat 作为基线；实验动机、数据配比、学习率、GPU 分配与判断标准见 [课程实验](../experiments/current/sft_curriculum/README.md)。

先比较新的开发题和原有 40 题一般交流开发集，再决定是否扩大训练。已审阅的旧 120 题只作历史回归。合成课程测试只证明对应任务的泛化，不能替代新的独立一般聊天验收，也不能据此宣称事实知识已经修复。
