# 工程与实验记录：让别人能看懂，也能复核

工程美观不是把代码写得短，而是让读者知道：输入是什么、哪一层负责什么、结果怎样被验证、失败时从哪里找原因。

## 按数据流读源码

| 顺序 | 模块 | 负责什么 | 不负责什么 |
|---|---|---|---|
| 1 | `models/llama_like` | 一次 forward、attention、loss 的数学 | 调度下载、发布模型 |
| 2 | `data`、`tokenizer` | 来源、清洗、编码、packing、读取 | 选择 optimizer |
| 3 | `training` | batch 分配、梯度、更新、验证、恢复 | 聊天语义评分 |
| 4 | `checkpoint` | 完整恢复、标准导出、云端归档 | 用上传成功判断模型好坏 |
| 5 | `posttrain` | 对话数据与 SFT | 修改预训练数据历史 |
| 6 | `evaluation`、`inference` | 固定题目生成、评分汇总、使用入口 | 反过来把最终测试当训练样本 |

在 `scripts/remote/week.py` 中可以看到长任务实际执行什么命令；`utils/workflow.py` 负责状态、日志和预算。控制器不隐藏模型数学，训练循环也不混入云端认证。

## 配置为什么与代码分开？

模型配置回答“网络长什么样”，训练 recipe 回答“怎样更新”。例如层数影响结构，LR 影响训练；把它们分开，比较两次实验时更容易发现真正的变量。

简单短跑用少量命令行参数；需复用的模型结构放 YAML。正式 checkpoint 保存完整运行约定和指纹，避免几天后只记得“差不多用了这些参数”。不把机器路径写进模型结构配置。

## 测试为什么先挑这些？

我们不靠“代码没有报错”判断正确。优先测会改变实验结论的边界：下一 token 标签是否错位、未来 token 是否可见、HF 映射是否一致、最后不足 batch 是否加权、空 rank 是否挂住、RNG 是否真正恢复。

这类测试可发现“训练还能跑，但其实在学错”的问题。文档改写则检查链接、命令与数据口径，不为了文字修改重复跑昂贵 GPU 测试。

```bash
ruff check src/dummym tests scripts
ruff format --check src/dummym tests scripts
pytest tests -q
```

函数用明确命名，核心接口标注类型。中文注释主要解释原因和形状，不逐行翻译语法。失败在输入边界尽早报告；小优化未通过时，回到已经验证的路线，并保留失败证据。

## 每个实验 README 的固定问题

1. **问题与动机**：哪项不确定性妨碍下一步？
2. **预期与设计**：希望观察什么，为什么采用这个对照？
3. **变量与条件**：改变什么，固定什么；有哪些无法完全固定的因素？
4. **指标与证据**：为什么选该指标，产物在哪里，结果是否完整？
5. **结论与边界**：支持什么，不支持什么；推测与观测分开。
6. **下一步**：怎样依据结果决策，而不是“再训练看看”。

结果未知就写待验证。设计理由不能反过来写成已经证实的优势；生成样例必须保留失败内容。可以提出“更多训练可能改善复读”的假设，但改善需要下一次实验实际观察。

## 怎样保持版本与成果一致？

关键代码与文档经检查后自动本地 commit；完成阶段会自动提交运行记录。原始语料、环境、缓存和恢复文件不进 Git。ModelScope 私有仓库保存关键 checkpoint、导出模型及同步指南，认证文件在源码树外。

`ready.json` 是“文件已经完整”的信号，不是“模型能力达标”的信号。预训练单文件 checkpoint 与 Trainer 的目录快照使用各自恢复方式，不能只因为都叫 checkpoint 就混用。

本轮预算最多七天，数据准备、训练、SFT 和评测分别有阶段限制。CPU 数据任务与 GPU 实验能独立时并行；等待必要数据时，不用重复无意义样本来伪造 GPU 利用率或训练量。
