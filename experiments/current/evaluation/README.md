# 评估设计：先冻结题目，再判断沟通能力

## 问题与原因

训练 loss 和用户体验不是同一指标。我们要直接检查日常交流、事实、指令、改写、摘要与三轮上下文，并避免只挑模型答得好的题。

## 为什么这样设计

正式训练前冻结 40 dev/120 test；最终六类各 20 项，保留 ID、rubric 和内容哈希。开发题用于选择，最终题不用于调参。多轮用模型实际历史回复，不注入正确答案。

自动检查空回答、复读、角色泄漏与上下文超限。语义审阅还要看事实、格式和原意，每项有实际证据的理由。未审阅的 None 不是通过。

## 已知结果与验收目标

数量、唯一性和哈希检查通过，说明题集结构可用；没有由此得到模型能力分数。总通过率 70%、各类 60%、结构正常 90% 是本轮目标，不是已达到的结果。

Base/Chat 的选择类辅助基准帮助观察变化，不能替代多轮验收。正式报告同时展示失败例子；若按测试结果继续改模型，应说明该测试已被看过。

证据 `evaluation/manifest.json` 和题集测试；评分格式见 [题集说明](../../../evaluation/README.md)，整体理由见 [评测阶段](../../../docs/07_evaluation_inference.md)。
