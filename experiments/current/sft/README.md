# 接口验证与后续对照：学习 assistant 回复

## 问题与原因

Base 学的是文章续写，我们要用对话示范教它回答。先确保 assistant 标签和保存恢复正确，再把真实会话用于正式训练。

## 设计理由

32 个合成会话、极小模型、四卡真实 TRL 训练，减少排障成本。明确检查 user 不被监督、assistant 被监督，以及模型保存和完整恢复字段。FP32 参数配合 BF16 计算，保护小 LR 下的细小更新。

正式阶段从同一 Base 做四档 LR 对照，各最多 50,000 个训练会话、一轮，再用固定开发题初筛。最后从 Base 开始四卡正式 SFT，最多两轮。会话不跨样例 packing，以简化角色和监督边界。

## 已知结果与未完成部分

四卡接口、assistant mask、保存及含四份 RNG 的 Trainer 快照通过，快照已上传。它是极小合成模型结果，不是 213M Chat 成果。

正式 LR 对照和真实开发回复已完成，结果见下节；正式全量训练和首轮语义验收已经完成：7,060 步，eval_loss=1.149027，语义通过率 38.3%，未达标。结构失败率和验证 loss 只帮助筛选，不能代替语义评分。

下一步检查是否实际遵循指令与上下文；失败例子也应保留。证据 `runs/sft-interface-smoke-v4/summary.json`，设计和恢复方式见 [SFT 阶段](../../../docs/06_sft.md)。

## 2026-10-06 的真实对照与修复

四档 LR 的验证 loss 依次为 1.533677、1.457459、1.415538、1.395623；40 项开发题结构失败比例依次为 27.5%、20%、27.5%、15%。本轮据此选 1e-4，尚不能把剩下 85% 当成语义通过。

全量正式任务曾在启动时失败：rank 0 的预处理超过其他 rank 的 600 秒 NCCL 等待窗口。小测试只说明接口正确，不能证明全量启动耗时也安全。修复为独立 CPU 预处理后再启动 DDP，保留原划分与监督规则；新增测试和四卡 smoke-v5 均通过，正式任务重试后已完成。详细证据见 [运行记录](../../../docs/results.md)。
